# US-089a game save data

`collectSave(world,options)` creates a `saveVersion:1` envelope over the public engine `serialize` result. Player world-space transform, hearts/mana and inventory/hand slots stay in the entity components already handled by WorldState; there is no second player-state copy to drift. Game data adds quest state, sorted unique opened-chest/dead-beast IDs, and slot metadata (player name/place/play time). The quest definition must accompany a quest state so restore validates its version/identity/completed prefix.

`applySave(save,assets,{questDef,worldOptions})` restores a fresh World through public `deserialize`, which invokes CO-5 `migrateState` internally. It returns the restored world, quest, chest/death IDs and metadata, with no aliases into the input. Runtime B1 hooks bind these game data back into the live systems. In particular, current beastSim creation intentionally resets beast health: B1 must suppress/reconcile saved dead IDs during sim construction, rather than assume the restored component alone prevents respawn. No sim/engine boot behaviour was changed here.

`stringifyGameSave`/`parseGameSave` validate envelope versions and produce canonical key ordering. Unknown future versions, nonfinite values, unsafe keys and non-JSON values fail explicitly. Valid WorldState v1 is accepted and migrated by apply; collected output is v2. Serialization is a save/load operation, not a per-frame path.

`createStorageAdapter(storage)` accepts a localStorage-compatible object provided by the platform caller; it does not access `window` or localStorage globals. `createMemoryAdapter` uses the same interface for tests. Three slots (indices 0/1/2) have separate keys; write/delete verify read-back. Empty slots, corrupt saves, denied reads, quota failures and silently dropped writes are distinguished with result objects. No save is written merely by importing this module; deletion requires an explicit caller action.
