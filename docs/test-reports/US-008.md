## Sandbox note on manual testing method

The browser pane's `requestAnimationFrame` loop is throttled/batched unpredictably by the automation sandbox: turning the player with a real, timed `ArrowRight` keydown/keyup did not match the expected `120°/s` arithmetic across two separate real-time holds (144° after 1.6 s, then 58° after a further 1.1 s — neither matches a steady 120°/s), and a later 1 s hold of `S` moved the player almost the full 15 m length of the room. This is the same rAF-throttling artifact already on record in the US-005 report, not a game bug (`game/js/physics/physicsTestMain.js`'s loop, fixed-step accumulator, and `game/js/entities/Player.js` are unmodified by anything I did).

Given that, I used two complementary methods, both against the real, unmodified integration path (`Player.js` + `capsule.js` + `Level.js` + `test_room.js`, the same modules `physics-test.html` uses):

1. **Live keyboard/mouse-equivalent input** in the browser pane (synthetic `KeyboardEvent('keydown'/'keyup')` dispatched on `window`, same as real key events, read via the page's own HUD) — used for the wall-hug/inner-corner checks below, real-time but with the throttling caveat noted above (labelled **synthetic, real-time** below).
2. **Deterministic scripted stepping**: in the same loaded page, dynamically imported `Level.js`, `Player.js`, `config.js` and `test_room.js` (no file edits) and drove `player.update(dt, controls, level)` in a fixed `1/60 s` loop for a known step count, exactly mirroring what `physicsTestMain.js` does per frame but without relying on rAF timing. Used for the pillar/doorway/platform/stair/low-wall/tunnelling checks (labelled **synthetic, deterministic** below).

All checks below ran against the unmodified game/engine code; nothing was edited to make the tests pass.
