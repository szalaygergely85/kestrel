## Bugs
- **BUG-1 [major] `?gpu=0` never visibly fades the 3D scene or sky**
  Steps: 1. Load `game/index.html?gpu=0&debug=1`. 2. Force/walk into the `end` trigger and let `quest.endT` run well past the 2 s fade (confirmed at `endT` up to 5-7 s). 3. Inspect the rendered frame / `rt.cells`.
  Expected: sky and terrain glyphs/colors step down the fade ramp toward black over 2 s, same as the GPU path (AC2: "fades to black... for both the 3D view and the text").
  Actual: sky cells stay exactly `bg=[196,220,239]` (unfaded light blue) and terrain glyphs keep their non-space characters indefinitely; nothing in the 3D view fades. Root cause: `engine/render/CellBuffer.js`'s `clear()` and `setCellRGB()` (the CPU raycaster's normal per-frame drawing path) set `cb.mask[i] = 1` on every cell, and `applySceneFade` (`engine/ui/fade.js` line 78: `if (mask[i]) continue;`) skips every masked cell — so on `?gpu=0` **all** cells are treated as "JS-owned, don't touch" and the fade is a full no-op for the 3D view. This is the same mask-conflation the programmer already found and worked around for the `?gpucompare=1` oracle (notes item 3: "clearing the mask... harmless in real gameplay, the GPU-DDA path never runs this CPU cast") — but `?gpu=0` **does** run this same CPU cast for real, on-screen rendering, so the workaround wasn't applied where it's actually needed. The default/shipping GPU path is unaffected (its own pass-F fade doesn't use `cb.mask`) and is verified working.
  Not blocking M1 shipping (per D-017, `?gpu=0` is a dev/debug switch only, no perf AC, and it isn't the path that ships), but it is an explicit tester-notes/AC line item ("both on the default GPU path and on `?gpu=0`") that currently fails, and the story's own PO-OK claims CPU fade was verified.

- **BUG-2 [minor, dev-tooling only] `window.__debug.world/playerHandle/look` go stale after a restart**
  Steps: 1. Reach the end, press `R`. 2. Read `window.__debug.look` / `window.__debug.world`.
  Expected: reflects the new world/look created by the `'world:loaded'` rebuild.
  Actual: `window.__debug.loop/world/playerHandle/look` are set once (`main.js` ~line 578-582), right after the *first* `engine.run(...)`, and never refreshed on restart; the live `look`/`world`/`playerHandle` used by the real per-frame closures are reassigned locally and diverge from the stale `window.__debug` copies (confirmed: setting `window.__debug.look.yawDeg` had no effect on player movement post-restart; `window.__debug.engine.world` is correct and can be used as a workaround). Does not affect gameplay or the F3 overlay (which reads the live closure variables directly), only external tooling reading `window.__debug` post-restart. Worth a one-line fix (re-assign these four fields inside the `'world:loaded'` listener) since it's the same hook the tester/future debugging relies on.
