## Bugs

- **BUG-1 [major] "Click to resume" pointer-lock overlay collides with the map card at 160x60, garbling both**
  Steps:
  1. Load `game/index.html?grid=160x60` and do **not** click (pointer lock stays unengaged, so `Click to resume` keeps showing – a normal, reachable state: the wake sequence takes ~8 s before the map card opens, so a player who hasn't clicked yet will see this).
  2. Let the wake sequence play through to the map card auto-open.
  Expected: the map card is fully readable, centred over the dimmed scene.
  Actual: the `Click to resume` plate (drawn unconditionally last, in `game/js/main.js:670` → `drawPauseOverlay`, whenever `!look.locked`, with no awareness of the map card/title/hints) is centred on the same row band as the map card's `Crown print:` line at 160x60 (60 total rows leaves little vertical clearance between the fixed `uiStyle.pause.row` and the card's centred position), so the two overlays print on top of each other and both are unreadable at that spot. Confirmed via screenshot (both texts visibly interleaved) with `M` closed and reopened – same collision each time the card is shown while pointer is unlocked. 240x90 and 320x120 have enough vertical room that the same two elements land on different rows and don't collide, so this only reproduces at 160x60.
  Root cause: `drawPauseOverlay` (`game/js/ui/pauseOverlay.js` + call site `game/js/main.js:670`) has no exclusion/dimming/z-order awareness of `engine/ui/panel.js` overlays (map card) or the title card – it always draws at a fixed `uiStyle.pause.row`. This predates US-015 (US-005) but the collision is only reachable now that a panel can be centred on screen during the unlocked-pointer window.
  Suggested fix (for the programmer, not attempted here): either skip/relocate `drawPauseOverlay` while `isMapOpen()`/title is active, or push a dim rect for the pause plate the way `pushHintDim`/`mapPanel.pushDim` already do so the two never literally share cells; whichever approach, keep it engine-agnostic (game-side, per D-006).

## Limitations / could not be verified

- **Pointer lock never engaged** in this automated browser (a documented limitation of the tool, also hit by the programmer). All "pointer locked" behaviour (e.g. hint `capture`/`M` gating relative to real mouse-look) was inferred from `world.state` and the `Input` module's internal flags rather than a true click-to-lock flow.
- **Real-time animation could not be watched continuously**: `requestAnimationFrame` stops advancing while the Browser pane tab isn't the fronted/visible one between tool calls, so a genuine "watch it play in real wall-clock time with the mouse" pass wasn't possible. Verification instead combined (a) driving the fixed-step loop manually (`loop._tick`, same dt the real loop would use) to advance `world.state['quest.wakeT']`/`['quest.endT']` to each phase, then (b) fronting the tab and screenshotting, plus (c) exact-colour verification via `rt.readbackPresent()` GPU-composited pixel reads. This is the same workaround the programmer used and documented in the story.
- **`M`-key automation flakiness**: `computer.key` (simulated OS-level keydown/keyup) reliably opened the card but sometimes did not register the close press; dispatching a `KeyboardEvent` directly via `window.dispatchEvent` was used instead and worked reliably both times. Likely a focus/target quirk of the automation tool, not a game bug (state and rendering both confirmed correct once the key event was actually delivered).
- **`Shift run` hint (10 s of walking) and literal WASD/jump input** were not driven through real key-hold + physics integration (would require sustained real-time input the throttled rAF makes impractical); relied on the passing `hints.test.js` unit coverage for that path instead of a live spot-check.
- Player-entity teleport (`playerHandle.data.transform.x/y`) was used in place of walking to reach `hintBurner`/`hintClimb`/`hintJump` – same shortcut the programmer's own verification pass used ("teleported the real player entity across the circle boundary rather than walking, to keep the session short").
