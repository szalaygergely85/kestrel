Confirmed: resizing the emulated viewport (1440x900, 720x450, 640x400) each produced a correctly re-sized canvas (`canvas.width/height` backing store scaled with `devicePixelRatio`, e.g. 720x450 CSS → 1440x900 backing at DPR 2). `?glyphs=1` screen (see below) shows fully-formed glyphs with no bleeding into neighboring cells at a 4x CSS-zoom inspection.

- [x] Demo screen: animated gradient + full glyph strip with per-cell fg/bg. Confirmed visually — animated diagonal color gradient plus a glyph strip render correctly with no console errors.
- [x] F3 toggles fps/frame-time overlay, top-left. Confirmed **functionally correct** but only by dispatching a proper `KeyboardEvent({code:'F3', key:'F3'})` from the page's own JS console, not via the automation tool's `computer` key-press action — see Bugs/Notes below for why. With a correct `code`, `preventDefault()` fires (`defaultPrevented: true`) and the overlay toggles on, showing `fps: 48.5 / frame: 18.77 ms / grid draw ... / cells: 160x60 / backend: gl2`. `Ctrl+F3` and `Ctrl+F` correctly do **not** get `preventDefault()` (pass-through verified).
- [x] Full 160x60 redraw performance (D-005 structural pass + this session's sandbox numbers).
  - Backend is `gl2` by default (`[RenderTarget] back-end: gl2` in console) on every load.
  - `?bench=1` (600 worst-case frames): `present()` avg **0.1 ms**, p95 **0.2 ms**, max **0.6–0.9 ms**, essentially flat between a 640x300 canvas (DPR 1.25) and a 1760x1140 canvas (DPR 1.25, emulated 1440x900 CSS window) — matches the PO's recorded sandbox numbers and the structural claim (one draw call, ≤80 KB upload, no per-frame allocation).

## Bugs
None blocking. One environment/tooling caveat, not a game bug:

- **Sandbox limitation, not a bug:** the Browser-pane `computer` tool's synthetic `key` action sends `KeyboardEvent.code === ""` for `F3` (only `.key` is set), so `game/js/engine/input.js`'s `GAME_KEYS.has(e.code)` check (which is correct per spec — it should key off `code`, not `key`, to be layout-independent) never matches, and the automation tool alone cannot toggle the overlay or verify `preventDefault`. Dispatching a realistic `KeyboardEvent` with a proper `code` field from the page's own console confirms the game logic itself is correct. Recommend future testers do the same when this sandbox is used, or use a real desktop browser for this specific check.

## Performance
- `present()`: avg 0.1 ms, p95 0.2 ms, max ~0.9 ms, flat across ~0.19M–2.0M backing pixels (sandbox `?bench=1`, gl2 backend). Meets D-005's structural criterion.
- Full rAF-loop frame (demo scene, not bench): ~18–19 ms/frame, ~48 fps observed in this sandbox — this reflects the sandbox's known-noisy overhead (documented by the programmer for Canvas2D and still visible here) plus the demo scene's own `setCell`-with-hex-string cost, not `present()`. Not used as the pass/fail signal per D-005 item 6.
- Real-desktop-Chrome `?bench=1` numbers are still outstanding (PO's "open, non-blocking" item) — I could not supply them from this sandbox either.

## Console errors
None observed on any tested path (default, `?bench=1` at two sizes, `?force2d=1`, `?glyphs=1`).

## Suggestions (non-blocking)
- Consider having `input.js` optionally also match on `e.key` as a defensive fallback for automation/testing tools that don't populate `code` for function keys (would not change real-browser behavior, since real browsers always populate `code`).
- The `fullFrame` bench number (which includes `fillWorstCase`'s `setCell`-with-hex-string cost) is easy to misread as the `present()` cost; consider labeling it more explicitly as "fill + present" in the on-screen bench output to avoid future confusion (already correctly documented in code comments).
