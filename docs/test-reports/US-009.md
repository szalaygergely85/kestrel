# Test report US-009 – Physics: jump, step-up, landing feel

Result: PASS

Criteria:
- [x] Step-up: floors up to 0.45 m climbed automatically, eye smoothed over 0.1 s, no snap – verified headless (max per-step eye delta on a 0.3 m stair riser: 0.0088 m, well under the 0.06 m bound; `stepOffset` converges to < 0.02 m within 0.1 s, monotonic, no overshoot) and confirmed 316/316 unit tests.
- [x] Jump on Space: 6.5 m/s initial velocity (6.167 after the documented same-step gravity integration), apex 1.003–1.056 m across runs, 100 ms coyote, 100 ms buffer – verified headless: press 1–5 steps after a drop still jumps, 7 steps after does not (100 ms coyote boundary); a mid-air press with no coyote does nothing; buffered press lands then jumps next step.
- [x] Air control 35% of ground acceleration – covered by `jump.test.js` item 5 (re-run, passing).
- [x] Gap AC4: all 11 walking take-offs (x = 8.70..9.00) clear the row-15 1 m gap (grounded, x ≥ 10, z ≥ 0, never z < -0.05), all 11 running take-offs clear the row-16 2 m gap (x ≥ 11) – verified headless against the live `test_room` level and `Player`/`EyeFeel` modules (22/22 pass).
- [x] Head clearance (AC5): jumping/walking under lintel `D` never has `footZ + 1.7 > ceilH + SKIN` while centered in `D`; jumping on `P` (ceilH 3.0) clamps at `maxZ = 1.3` exactly and lands back on `P` with `vz = 0` on the clamp step.
- [x] Pit AC6: floor raised to -0.6 m confirmed in `test_room.js`; holding into the pit wall for 2 s does not climb out (0.6 m > 0.45 m step-up); jumping out west and east both succeed within 1.5 s.
- [x] No-bridge AC7: 10/10 runs across the row-15 gap at run speed without Space end grounded in the pit at z = -0.6, x = 9.7 (blocked before reaching the far side) – matches the test plan's negative control exactly.
- [x] Landing dip / head bob AC8: flat jump (~1.05 m fall) dips to -0.08 m and fully recovers to 0 afterward; head bob amplitude ±0.03 m while walking, exactly 0 while standing still; `headBobCyclesPerMeter` = 0.8 (within the PO's 0.7–1.0 range).
- [x] No double jump / no auto-repeat (AC9): holding Space for 3 s from the floor produces exactly one jump; releasing and re-pressing jumps again.

Suites: `node game/js/physics/physics.test.js` 187/187, `node game/js/physics/jump.test.js` 111/111, `node game/js/entities/eyeFeel.test.js` 18/18 – 316/316, all green.

Bugs:
- BUG-1 [minor, environment-only, non-blocking] The sandbox browser's `:8000` origin kept serving the pre-US-009 `Player.js`/`physicsTestMain.js` (old, no `coyote`/`buffer`/`feel` fields) even after restarting the local `python -m http.server` process on the same port and hard-refreshing (`Ctrl+Shift+R`) – network tab showed fresh `200 OK` bodies matching the old file, and the live `Player` instance in the page had no `coyote`/`buffer`/`feel`/`jumped`/`landed` fields, throwing `Cannot read properties of undefined (reading 'toFixed')` in `physicsTestMain.js:93` (the HUD line) every frame. This exactly matches the programmer's documented caveat in the backlog (heuristic origin-level caching in this sandbox, no `Cache-Control` header from the stdlib server). Fix: serving from a brand-new port (8123 instead of 8000) immediately loaded the correct US-009 code with zero console errors. This is a test-tool/sandbox artifact, not a product bug – flagging only so a future tester on this same sandboxed environment doesn't mistake it for a regression. A real developer's browser (not this sandbox's persistent-origin cache) is very unlikely to hit this.

Performance: fps reported by the harness's own counter and the game's debug HUD was low (9–13 fps) in this sandboxed remote-browser environment; this is consistent with automation/screenshot overhead in the browser tool, not the physics code (all 316 headless checks and the deterministic 600-step-equivalent driven checks above ran without any dropped logic, and the physics loop is a fixed-step accumulator decoupled from render fps). No stutter observed in the fixed-step values across any of the driven runs.

Console errors: none, once served from an uncached port (see BUG-1). `game/physics-test.html` and `game/index.html` both loaded and accepted WASD/Space input with zero console errors afterward.

Notes on method: browser automation in this environment (`rAF`/timed key presses) is unreliable for exact-frame assertions, so the gap/coyote/buffer/no-bridge/pit/lintel/landing-dip/head-bob/step-smoothing checks above were driven deterministically by importing the real `game/js/entities/Player.js` and `game/js/physics/config.js` modules in the live page and calling `player.update(dt, controls, level)` directly in a fixed 1/60 s loop against the real `test_room` level object (`window.__physicsDebug.level`) – labelled **synthetic** throughout, same technique the programmer used for their own browser verification. A real Space keypress was also dispatched through the harness's own `keydown` listener (not `document.dispatchEvent`, which the page's own listener didn't pick up reliably – another sandbox quirk) and confirmed a real jump/land/recover cycle on the HUD (`fallDistance` 1.00 m, `eyeOffset` back to 0.000 m).
