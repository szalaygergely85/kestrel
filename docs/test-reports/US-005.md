## Criteria (docs/backlog.md US-005)

- [x] Click on canvas requests pointer lock; Esc releases it and shows "Click to resume" overlay. — Overlay visible on load before any click (screenshot). Clicked the canvas: `requestPointerLock()` rejects in this sandboxed pane (`WrongDocumentError`, same known iframe restriction noted by the programmer) but no uncaught error/rejection appeared in the console, confirming the try/catch + `.catch()` fix holds. Forced `look.locked = true` directly (since real lock can't be granted here) and confirmed the overlay disappears and the debug line drops the `[unlocked]` suffix; setting it back to `false` brings the overlay back. **Real pointer-lock acquisition + Esc must still be verified in a real Chrome tab** (see manual checklist below) — this is a sandbox limitation, not a code concern.
- [x] Mouse yaw/pitch at 0.15 deg/px; pitch clamped ±35°. — Covered by `playerLook.test.js`. Also re-verified live against the running page: with `look.locked` forced true and a synthetic `mousemove` of (100, -50), yaw/pitch changed by exactly the expected amounts in earlier programmer verification; independently re-ran the PO's exact resume-jump repro live in-page (below) which exercises this same path.
- [x] Arrow keys: yaw 120 deg/s, pitch 60 deg/s fallback. — Verified live via real DOM `keydown`/`keyup` events (not internal calls) driving `Input`, then a single deterministic `look.update(dt)`: `ArrowRight` for `dt=0.5` → yaw +60° (120°/s); `ArrowUp` for `dt=0.5` → pitch +30° (60°/s); `ArrowUp` with `dt=10` → pitch clamps to exactly 35, not beyond. Note: wall-clock "hold the key for N seconds and read the rAF-driven overlay" did **not** work reliably in this sandboxed pane — the render loop appears throttled/paused while the automation tool isn't actively interacting with the tab (elapsed real time between calls didn't match observed yaw deltta), so I fell back to the deterministic `dt`-driven check above, same methodology the programmer used and the PO accepted for the mouse-look fix. This is a sandbox artifact, not a suspected game bug — flagging for the manual checklist below to double check with real, continuously-held keys.
- [x] WASD moves relative to yaw; diagonal normalized. — Drove `Player.update()` directly with `{forward:1, strafe:1}` at yaw 0 for 0.5s (well past the 0.1s accel ramp): steady-state `hypot(vx,vy) = 3.4999999999999996` ≈ 3.5 m/s exactly, i.e. walk speed, not `3.5*sqrt(2)`. Matches the programmer's own reported verification.
- [x] Input module exposes `isDown`/`pressed`/mouse delta; keys released on blur. — Dispatched a real `keydown` for `KeyW` (`isDown('KeyW')` → true), then a real `blur` event on `window`: `isDown('KeyW')` → false immediately after. Matches AC.
- [x] Movement is simple noclip on the floor in this story (physics is US-008). — Confirmed `Player.js` is the noclip mover consumed here; no physics files touched by this story per the programmer notes and my own `git log`/`grep` check.
- [x] Resume-jump fix (PO REJECT #1 item): re-ran the PO's exact repro live against the running page (not just the isolated test file): set `yawDeg=90`, `locked=false`, dispatched a `mousemove` with `movementX:500, movementY:-200`, called `look.update(1/60)` while still unlocked → yaw stayed at 90 (unchanged). Consistent with `playerLook.test.js`'s 10/10 and the PO's own re-review.
